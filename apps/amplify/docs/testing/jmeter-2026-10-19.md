# JMeter performance run, 19 October 2026

**Why this run:** check that the JMeter suite still works after the backend moved to marketing-tools `apps/amplify` (ADR-033), and record p95/p99 for every module after the people-directory, link-check and leaderboard ETag changes.

**Result:** the suite works from the new location after two stale expectations were fixed. On a warm stack, all four modules meet the p95 < 50 ms target with no errors. Two endpoints are just over at the endpoint level: the rejected-token path (55 ms) and the nightly partition maintenance write (56 ms). Neither is a phase 1 user read. p99 sits at 84–329 ms across endpoints, the same shape as the k6 run on 17 October: the long tail comes from the laptop's Docker VM and the JVM, not the database.

## Run 1: cold, right after a rebuild

`make up` had just rebuilt every image, so the JVMs started cold. 17 of 19 endpoints were over p95 50 ms (module p95 56–67 ms, p99 359–388 ms). The latency is mostly warm-up; run 2 is the comparable number.

It also showed two **functional** failures, both stale test expectations rather than product bugs:

| Endpoint | Expected | Got | Why | Fix |
|---|---|---|---|---|
| `common/problem-not-found` (`GET /campaigns/does-not-exist`) | 404 | 400 | A malformed campaign id is 400, as `openapi.yaml` says (changed in the 2026-10-17 deep review) | Use a well-formed UUID that matches nothing |
| `jobs/partitions` (`POST /maintenance/partitions`) | 200/202/204 | 201 | amplify-jobs answers 201 Created | Accept 201 |

Both fixed in `gen-master-plan.py`; `master.jmx` regenerated.

## What it means

- **Phase 1 reads meet the target.** The Celebrate page's calls (`/leaderboard` 46 ms, `/me` 41, `/campaigns` 36, `/me/shares` 34, `/categories` 40) are all under p95 50 ms with 1,000 employees and 50,000 ledger rows. `/leaderboard` now also does the team lookup and the per-viewer ETag hash; it stayed under.
- **Tight spots.** `/me/points` (49 ms) and `/team` (49 ms) sit right on the line, as `/team` did in the 17 October k6 run (50–77 ms). Both are close enough that a busier machine tips them over. Re-measure in Choreo dev.
- **The two "over" endpoints aren't user reads.** `common/unauthenticated` is the 401 path for a request with no valid token (55 ms; not profiled). `jobs/partitions` is the nightly maintenance write (56 ms), called once a night by the scheduler.
- **p99 is the laptop.** Every endpoint, including `/health` (p99 128 ms, p50 2 ms), has a tail of 60–330 ms with p50 in single digits. Work that trivial doesn't have a database cause; it's the shared Docker VM and JVM pauses, with other containers busy on the same machine. Choreo's numbers are the ones that count for p99.

## Follow-ups

- Re-run in Choreo dev (one replica, then two) before go-live; record p95 and p99 the same way. That decides `/team` and `/me/points`.
- If p99 matters for the pilot (it mostly doesn't for a leaderboard), try JVM flags in the images (heap size, G1 pause target) and measure again.
- Run JMeter with `SEED=1` only on a stack you don't mind losing data on, or back up first: the seed adds 1,000 employees to the leaderboards and nothing removes them.
