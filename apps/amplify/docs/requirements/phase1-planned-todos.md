## MVP definition

> **Phasing updated 2026-10-19** (Requirements / Phase Breakdown): phase 1 = register posts with category/priority, share new posts to the Club Chat space, link LinkedIn, record reposts, individual and team leaderboards. External shares (item 3), PO adjust/reverse and the PO dashboard (item 4) move to phase 3 (own posts, scoring rules, PO edits) and phase 2 (points/Coins history, reports). The backend for them is built; phase 1 ships no UI for them. Items below are kept as written for history.

Phase 1 is done when, in Choreo **prod**, for a pilot group:

1. Marketing registers an official WSO2 LinkedIn post as a Campaign, and a card lands in the WSO2 Club Google Chat space.
2. An employee connects LinkedIn once, then shares or reposts that Campaign from One WSO2. Amplify publishes it on their LinkedIn and awards points automatically.
3. An employee submits an external share (their own post, blog or article about WSO2) from My Campaign. PO approves or rejects it, and approval awards points. Reposts made in the LinkedIn app aren't tracked in phase 1 (A3, future phase).
4. Everyone sees three leaderboards: company top N (default 3), their personal standing, and My Team (B15). PO can adjust or reverse points with a reason, and every change is audited. PO has a phase 1 dashboard (B6); SLT reports are phase 2.
5. Points are **held** in the ledger and shown as points only, no Coin value (A11). 
6. The same container images run locally (Docker Compose), in Choreo, and later in OpenChoreo without code changes.

Out of phase 1 (do not build): the Novera agent/classifier/LLM gateway/AMP/ThunderID (Novera's announcement card is the exception, [M6c](#m6c--announce-through-novera-2026-10-22)), queue service, Community Management engagement sync (reactions, comments, native reposts), Coin issuer, HR Entity sync, team/location dashboards, SLT reports, employee data-deletion/anonymize path, other social platforms.

## Architecture at a glance

**One cell = one Choreo project (`Amplify`).** The cell owns its data. An **API proxy at the cell edge** is the only way in. One WSO2 never calls `amplify-api` directly.

```text
 ┌─ One WSO2 (existing) ───────┐
 │ React SPA · Amplify module  │
 │ Asgardeo sign-in            │
 └──────────────┬──────────────┘
                │ HTTPS · Asgardeo bearer · OHS/PL (OpenAPI 3)
                ▼
 ┌──────────── Cell: Amplify (Choreo project) ──────────────────────────────────────────┐
 │  Amplify API Proxy  (Choreo API Proxy · local: WSO2 API Manager 4.7.0)               │
 │   auth · scopes · rate limit · security headers · subscriptions                      │
 │        │ Project visibility                                                          │
 │        ▼                                                                             │
 │  Amplify Backend = amplify-api (Ballerina Service)                                   │
 │   modules = bounded contexts: campaign · connection · sharing · external_sharing ·   │
 │   scoring · recognition · announcements                                              │
 │        │ POST /runs ("Save & Share Now")             ┌──────────────────────────┐    │
 │        │   amplify-api ── schedule sync (ADR-026) ──►│ Amplify Scheduler        │    │
 │        ▼                                             │ akorn/scheduler 1.7.8    │    │
 │  Amplify Jobs = amplify-jobs (Ballerina Service) ◄───┤ no API auth: Project only│    │
 │   outbox drain · LinkedIn adapter · Chat notifier ·  │ POST /runs               │    │
 │   scoring · token-partition upkeep                   │ POST /maintenance/...    │    │
 │        │                                             │ own Postgres DB + user   │    │
 │        │                                             └──────────────────────────┘    │
 │        ▼                                                                             │
 │  PostgreSQL (Choreo-managed, Aiven) · schema per bounded context                     │
 │   connection.provider_token = daily partitions, dropped after expiry + grace         │
 └──────┬──────────────────────────────────────┬────────────────────────────────────────┘
        │ egress (declared, circuit-broken)    │
        ▼                                      ▼
  LinkedIn API + OAuth (prod)            Google Chat incoming webhook (Club space)
  mock-linkedin (dev / local)            test space (dev / local)
```

Cell rules:
- **Single ingress:** only the API proxy is exposed (Organization/Public). `amplify-api`, `amplify-jobs`, the scheduler and Postgres stay at Project visibility. The scheduler's API has no auth, so it is never published and only `amplify-api` calls it (ADR-026).
- **Owned data:** only `amplify-api`, `amplify-jobs` and the migration task connect to the Amplify database. The scheduler has its own database and user.
- **Declared egress:** LinkedIn and Google Chat are Choreo connections with per-environment URLs and secrets. Every outbound call goes through a circuit breaker.
- **Bounded contexts as modules first.** Each context is a Ballerina module with its own Postgres schema, so any one can be lifted into its own component later without changing the cell's published API.
- **Portable by default:** container + env vars + OpenAPI + cron string (in `config.app_setting`, pushed to the scheduler). Nothing Choreo-only in the code.

## Roles and access

Asgardeo groups, with the same names in the prod org and the non-prod (dev/local) org. Roles add to the employee baseline.

| Persona | Role | Can do |
| --- | --- | --- |
| Employee | *(no extra role)* | Connect/remove LinkedIn, share campaigns, submit external shares, see leaderboard and own points |
| PO | `amplify_po` | Review external shares, allocate/adjust/reverse points, **point rules** (A5), **register and edit campaigns** (A6), PO dashboard |
| Marketing | `amplify_marketing` | Register and edit campaigns, Save & Share Now, category list |
| SLT | `amplify_slt` | Read-only reports (participation, reach, points per campaign). Role created now; reports ship in phase 2 |
| Admin | `amplify_admin` | Settings (leaderboard top N, run schedule (live-applied, ADR-026), reminder days, campaign default window), failed announcements, kill switches |
